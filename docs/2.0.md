
6. 7. - # 基于区块链的跨医院医疗数据可信共享系统软件规划书与实施方案
      
        ---
      
        ## 1. 绪论与系统建设目标
      
        ### 1.1 研究背景与痛点分析
      
        随着现代医疗信息化建设的持续深入，电子病历（EMR）、检验检查报告以及医学影像等数据已成为支撑临床诊断、多学科联合会诊（MDT）及医学科研的核心要素。然而，受限于各医疗机构信息系统的自治性、技术壁垒以及数据安全合规要求，医疗数据跨机构流转面临严峻挑战：
      
        * **跨机构数据孤岛显著**：患者转诊或异地就医时，既往病史与检验报告分散在不同医院，导致重复检查频发与医疗资源浪费。
      
      
        * **中心化存储面临单点失效与泄露隐患**：传统中心化数据库易遭黑客攻击、拖库勒索及内部特权人员的越权调阅。
      
      
        * **数据防篡改与司法存证能力缺失**：传统数据流转各方缺乏防篡改验证技术，医疗争议中电子证据的可信度难以自证。
      
      
        * **访问控制与患者主权约束粗放**：传统基于角色的访问控制（RBAC）缺乏机构、科室等多维环境属性约束，且往往忽视患者本人的知情授权意愿。
      
      
        * **突发急救场景下缺乏弹性处置机制**：若严格限制必须获得患者在线授权，在患者突发昏迷、休克等危急场景下，医生将陷入“因无法取得授权而不能调阅关键病史（如过敏史、严重慢性病史）”的救治死锁；若无限制放开，又会导致权限失控与滥用风险。
        * **审计追踪流于形式**：业务日志易被篡改或覆盖，缺乏多方监管与闭环追责依据。
      
        
      
        ### 1.2 系统建设目标
      
        本系统面向多医疗机构间的数据协同共享需求，模拟医院A、医院B、医院C三方参与的联盟网络。系统紧扣软件工程规范，达成以下目标：
      
        1. 实现医疗数据“**链下密文存储（IPFS）+ 链上凭证锚定（Fabric）**”，既规避大文件上链导致的账本膨胀，又保证数据不可篡改与可信验证。
      
      
        2. 构建以“**统一安全网关**”为核心的递进式访问控制体系（RBAC + ABAC + 患者显式授权），杜绝跨模块重复鉴权。
      
      
        3. 建立轻量严密的**紧急访问（Break-Glass Emergency Access）机制**：在常规授权不满足且危及患者生命时，允许医生经身份核验并签署临床责任声明后临时调阅数据，同步触发双向通知、多级惩戒与监管追责闭环。
        4. 提供受控的 **AI Agent 自然语言辅助查询**：AI 服务严禁直连底层数据库，仅通过 Tool Calling 机制携带用户身份 Token 调用 Go 后端业务接口，在保证安全边界的前提下提升交互体验。
      
        
      
        ### 1.3 开发边界控制（严格禁止增加的功能清单）
      
        为避免毕业设计范围失控与架构过度设计，系统坚决锁定边界，开发时**严格禁止**引入以下内容：
      
        * **架构层禁止**：禁止引入 Spring Cloud/K8s/微服务集群（统一采用单体分层 Go Gin 架构）、禁止开发移动端原生 App 或微信小程序（统一使用 Vue3 PC Web 端）。
      
      
        * **算法层禁止**：禁止使用神经网络、随机森林、深度学习等黑盒机器学习模型做风险预测（全面采用规则固定的加权风险评分引擎）；禁止引入复杂的密文检索或高级同态加密研究。
      
      
        * **业务层禁止**：禁止对接真实 HIS/PACS 生产系统，禁止采集真实患者隐私数据（统一使用规范的模拟脱敏数据）；禁止处理超大体积 DICOM 影像序列流与 3D 渲染（统一规范为 PDF 检验单、PNG/JPG 报告与切片）；禁止赋予 AI Agent 自动诊断、疾病预测、处方推荐或自动授权等医疗决策行为。
      
      
        * **区块链层禁止**：Fabric 联盟链采用单通道多组织架构（One Channel, 3 Orgs），不进行复杂的跨链桥或动态分片开发。
      
      
        * **外设服务禁止**：禁止接入商业短信网关、在线支付系统及真实第三方身份认证平台。

        ## 2. 系统总体架构与技术选型
      
        ### 2.1 系统逻辑分层架构
      
        系统遵循“控制流与数据流分离、业务逻辑与安全网关收口”的原则，自上而下划分为四层架构：
      
        ```text
               ┌────────────────────────────────────────────────────────┐
               │   前端展示层 (Vue3 + TypeScript + Element Plus + Pinia) │
               │     医生工作台  |  患者中心  |  管理员控制台  |  监管审计台    │
               └───────────────────────────┬────────────────────────────┘
                                           │ RESTful API (HTTPS + JWT Bearer Token)
               ┌───────────────────────────▼────────────────────────────┐
               │     Go 核心业务服务层 (Gin Web Framework + GORM)        │
               │  ┌──────────────────────────────────────────────────┐  │
               │  │       统一安全与权限网关 (Single Gatekeeper)      │  │
               │  │    AuthService ──► PermissionService (RBAC/ABAC) │  │
               │  │    ──► AccessEngine (患者授权 / Break-Glass)      │  │
               │  │    ──► RiskEngine (固定规则加权评分引擎)          │  │
               │  └──────────────────────────┬───────────────────────┘  │
               │                             │ 放行 (ALLOWED)           │
               │  ┌──────────────────────────▼───────────────────────┐  │
               │  │                  核心纯净业务服务                 │  │
               │  │  MedicalService  │  CryptoService  │ IPFSService │  │
               │  │  BlockchainService (Fabric)        │ AuditService│  │
               │  └──────────────────────────────────────────────────┘  │
               └───────┬──────────────┬─────────────┬─────────────┬───────┘
                       │              │             │             │
               ┌───────▼──────┐ ┌─────▼─────┐ ┌─────▼─────┐ ┌─────▼─────┐
               │  MySQL 8.0   │ │ Redis 7.0 │ │IPFS Node  │ │Fabric 2.5 │
               │ (9张核心表)  │ │(Token/频控)│ │ (加密密文) │ │(可信账本) │
               └──────────────┘ └───────────┘ └───────────┘ └───────────┘
                                                                   ▲ Tool Calling
                                           ┌───────────────────────┴──────┐
                                           │ AI 辅助层 (Python + FastAPI) │
                                           │ LangChain Agent (仅做语义解析) │
                                           └──────────────────────────────┘
        
        ```
      
        * **前端展示层**：基于 Vue 3 + TypeScript + Element Plus 构建，按医生、患者、管理员、监管人员四类角色实现路由守卫与动态菜单挂载。
      
      
        * **Go 核心业务服务层**：基于 Gin 框架，采用 Controller-Service-Repository 分层模式。所有外部请求必须先通过统一安全网关，底层业务 Service 不写任何重复鉴权代码，专注实现业务逻辑。
      
      
        * **数据与基础设施层**：
        * **MySQL 8.0**：持久化存储用户、机构、科室、病历元数据、授权策略、紧急事件单及全生命周期审计日志。
      
      
        * **Redis 7.0**：负责 JWT 吊销黑名单、API 频控滑动窗口计数器以及并发分布式锁。
      
      
        * **IPFS（Kubo 独立集群节点）**：去中心化持久化存储经 AES-256-GCM 加密后的病历文件与影像密文，返回唯一内容标识符 CID。
      
      
        * **Hyperledger Fabric 2.5 LTS**：配置三组织（OrgA、OrgB、OrgC）与 Raft 排序服务，通道（`medicalchannel`）维护不可篡改的可信存证、授权凭据、紧急事件记录及操作审计凭证。
      
        
      
      
        * **AI 辅助层**：基于 Python 3.10 + FastAPI 独立部署，通过 LangChain 实现自然语言意图理解与 Tool Calling 编排。AI 进程**不配置任何数据库连接驱动**，强制通过 HTTP 携带用户 Token 请求 Go 后端 API。
      
        
      
        ### 2.2 用户角色与权责划分
      
        系统只设置以下四类核心角色，严禁职责混淆与跨界：
      
        | 角色     | 角色标识 | 主要功能权限与职责边界                                       |
        | -------- | -------- | ------------------------------------------------------------ |
        | **医生** | `doctor` | 录入并上传患者医疗数据、发起跨机构调阅申请、在危急救治场景下提交紧急访问申请。 |
      
         |
        | **患者** | `patient` | 查阅个人电子健康档案、管理授权策略（新增、撤销）、接收紧急访问通知并反馈无异议或提出异议。
      
         |
        | **管理员** | `admin` | 维护用户账号、医院机构、科室字典；依据监管审核裁决执行账号状态的解封或管理，**严禁查看病历实体与越权审批医疗合规事件**。
      
         |
        | **监管人员** | `supervisor` | 查看全局可信审计日志、查看区块链存证及交易大屏、审核紧急访问（Break-Glass）事件并下达合规或违规处置判定。
      
         |

        ## 3. 核心算法与机制设计
      
        ### 3.1 链上链下协同存储与完整性校验机制
      
        #### 3.1.1 协同存储流程
      
        医疗原始数据包含敏感个人身份信息（PII）且体积极大，系统采用“链下密文存储 + 链上凭证锚定”机制：
      
        1. **本地对称加密**：医生端上传原始医疗文件 $\text{PlainData}$，后端 CryptoService 动态生成 256 位随机对称密钥 $K$ 与 96 位初始化向量 $IV$。采用 AES-256-GCM 算法进行带附加验证数据（AAD）的加密计算，将患者 ID 与记录编号绑定进 AAD，输出密文数据 $C$ 与 16 字节认证标签 $T$：
      
        
      
        $$C, T = \text{AES-GCM-Encrypt}(K, IV, \text{PlainData}, \text{AAD})$$
      
      
        2. **原始明文哈希计算**：对原始明文数据进行单向 SHA-256 计算，生成用于抗篡改举证的基准数据指纹 $H_{\text{raw}}$：
      
        
      
        $$H_{\text{raw}} = \text{SHA-256}(\text{PlainData})$$
      
      
        3. **链下持久化存储**：将密文 $C$ 与标签 $T$ 组合存入 IPFS 节点，获得内容寻址唯一编码 $CID$。
      
      
        4. **业务关系存储**：将病历编号、患者 ID、CID、文件大小等元数据存入 MySQL 的 `medical_records` 与 `medical_files` 表。
      
      
        5. **联盟链交易锚定**：组装链上存证资产 `MedicalAsset`（包含 RecordID、PatientID、CID、$H_{\text{raw}}$、HospitalID、CreatorID、Timestamp），通过 Fabric Gateway 提交智能合约写入分布式账本，获取全局唯一交易凭据 TxID 与区块高度。
      
        
      
        ```text
        [原始医疗文件] ─── SHA-256 计算 ──────────────────────────────► H_raw (基准指纹) ──┐
            │                                                                         │
            ▼                                                                         │
        AES-GCM 加密 ──► [密文文件] ──► IPFS 存储 ──► 返回 CID ──────────────────────────┴─► 写入 Fabric 链码
                                                                                             (MedicalAsset)
        
        ```
      
        #### 3.1.2 动态完整性验证流程
      
        当监管人员或医生需要确认病历真实性时，执行以下核验逻辑：
      
        1. 传入病历编号 RecordID，从 MySQL 查询该记录对应的 IPFS $CID$。
      
      
        2. 系统调用 IPFSService，依据 $CID$ 从 IPFS 集群拉取密文数据，并配合密钥解密生成临时明文 $\text{PlainData}'$。
      
      
        3. 本地计算当前解密明文的 SHA-256 摘要值：
      
        $$H_{\text{calc}} = \text{SHA-256}(\text{PlainData}')$$
      
      
        4. 通过 Fabric Gateway 调用链码查询该记录固化在区块账本中的原始摘要值 $H_{\text{chain}}$。
      
      
        5. 比对结论输出：
      
        $$\text{Result} = \begin{cases} \text{Verified (数据真实完整)}, & H_{\text{calc}} == H_{\text{chain}} \\ \text{Tampered (数据已被篡改)}, & H_{\text{calc}} \ne H_{\text{chain}} \end{cases}$$
      
      
        6. 核验完成后，结果由统一审计服务记入审计日志；若比对失败则自动触发高危安全告警。

        ### 3.2 复合访问控制模型与紧急访问机制（Break-Glass）
      
        #### 3.2.1 统一权限判定流水线
      
        系统拒绝在各个 Controller 或 Service 内散落鉴权逻辑，统一由 `AccessEngine` 按照流水线进行递进判定：
      
        ```text
                          医生发起跨机构调阅请求
                                    │
                                    ▼
                      ┌───────────────────────────┐
                      │  第一层：RBAC 角色拦截器   │ ──(非 doctor 角色)──► 阻断 (403 Forbidden: 角色权限不足)
                      └─────────────┬─────────────┘
                                    │ 通过 (具备合法医生角色)
                                    ▼
                      ┌───────────────────────────┐
                      │  第二层：ABAC 属性规则匹配 │ ──(属性不匹配)──────► 阻断 (403 Forbidden: 机构/科室/状态受限)
                      └─────────────┬─────────────┘
                                    │ 通过 (执业正常、科室具备调阅权限)
                                    ▼
                      ┌───────────────────────────┐
                      │  第三层：患者显式授权检查  │
                      └─────────────┬─────────────┘
                                    │
                    ┌───────────────┴───────────────┐
                    │ 存在有效授权                  │ 无有效授权 / 患者无法在线确认
                    ▼                               ▼
          ┌──────────────────┐            ┌───────────────────────────────────┐
          │ 动态规则风险引擎 │            │ 触发分支：是否声明紧急访问？      │
          └─────────┬────────┘            └─────────────────┬─────────────────┘
                    │                                       │
             ┌──────┴──────┐                        ┌───────┴───────┐
             │ 评分 < 30   │ 评分 >= 30             │ 否 (常规拒绝) │ 是 (申请 Break-Glass)
             ▼             ▼                        ▼               ▼
        [直接允许访问] [中高风险处置]          [阻断 (403: 未授权)] [进入紧急访问闭环流程]
        
        ```
      
        * **第一层（RBAC 粗粒度过滤）**：校验 JWT 身份，操作主体必须具备 `doctor` 角色，其他角色直接拦截。
      
      
        * **第二层（ABAC 细粒度环境过滤）**：
        * 主体机构状态正常（Status = 1）且接入联盟链白名单；
      
      
        * 调阅科室与病历所属科室满足跨科互认准入关系；
      
      
        * 医生个人执业状态正常（Status = 'NORMAL'），未处于 `RESTRICTED` 或 `DISABLED` 状态。
      
      
        * **第三层（患者显式授权比对）**：
        * 匹配有效性：验证 `authorizations` 表中是否存在针对该医生或该医院的授权条目；
      
      
        * 时效区间：`StartTime <= Now <= EndTime`；
      
      
        * 范围覆盖：`Scope == "ALL"` 或目标病历属于 `SINGLE` 授权项；
      
      
        * 状态正常：`Status == "ACTIVE"`（未被患者撤销）。
      
        
      
        
      
        #### 3.2.2 紧急访问（Break-Glass Emergency Access）执行闭环
      
        针对患者昏迷、突发危重疾病、急诊抢救等无法及时在线授权的极端场景，系统在跨机构访问模块中内置轻量规范的紧急访问机制：
      
        ```text
        [常规授权检查失败 (未授权)] ──► 前端界面弹出【申请紧急访问】入口
                                                  │
                                                  ▼
                                    ┌───────────────────────────┐
                                    │ 医生填写紧急访问申请单    │
                                    │ 1. 紧急原因 (昏迷/抢救/危重)│
                                    │ 2. 填写临床救治说明       │
                                    │ 3. 勾选合规法律责任声明   │
                                    └─────────────┬─────────────┘
                                                  │ 提交申请
                                                  ▼
                                    ┌───────────────────────────┐
                                    │ 后端执行基础身份前置安全核验│
                                    │ (医生合法? 机构正常? 未受限?)│
                                    └─────────────┬─────────────┘
                                                  │ 核验通过
                                                  ▼
                                    ┌───────────────────────────┐
                                    │ 1. 允许访问并解密核心病历  │
                                    │ 2. 生成紧急访问事件单     │
                                    │ 3. 关键存证写入 Fabric 账本│
                                    └─────────────┬─────────────┘
                                                  │
                            ┌─────────────────────┴─────────────────────┐
                            ▼                                           ▼
              ┌───────────────────────────┐               ┌───────────────────────────┐
              │ 异步通知患者端            │               │ 监管后台展示待审核卡片    │
              │ "您的数据被执行紧急调阅"  │               │ 标红提示【紧急访问待审核】│
              └─────────────┬─────────────┘               └─────────────┬─────────────┘
                            │                                           │
              ┌─────────────┴─────────────┐                             │
              ▼                           ▼                             ▼
        【确认无异议】             【提出异议投诉】              ┌───────────────────────────┐
              │                           │                       │ 监管人员独立调阅审查      │
              └─────────────┬─────────────┘                       │ (医生/原因/病历/患者反馈) │
                            │                                     └─────────────┬─────────────┘
                            └───────────────────┬───────────────────────────────┘
                                                ▼
                                  ┌───────────────────────────┐
                                  │ 监管人员执行审核裁决      │
                                  └─────────────┬─────────────┘
                                                │
                                 ┌──────────────┴──────────────┐
                                 ▼                             ▼
                     [判定正常: 真实急救调阅]       [判定可疑/违规: 虚假救治套取]
                                 │                             │
                                 ▼                             ▼
                     事件结案 (已确认关闭)          事件标记 (待调查 / 确认违规)
                                 │                             │
                           正常归档存证             系统分级实施账号惩戒
                                                    (警告 / RESTRICTED / DISABLED)
        
        ```
      
        **紧急访问的设计细节与处置规则**：
      
        1. **前置安全过滤**：紧急访问并非无条件放行，系统必须严格前置核验：①医生身份真实合法；②所属医疗机构处于正常服务状态；③医生未被处于限制执业状态。任何一项不满足，直接拒绝发起。
        2. **两阶段责任固化**：医生端必须填写临床说明并勾选“我确认本次访问仅用于紧急医疗救治”，防止随手误触，固化法律责任。
        3. **数据解密与双重记账**：系统临时生成解密凭证放行数据，并在 MySQL 的 `emergency_access_events` 表生成事件单，同时通过智能合约将事件核心摘要（EventNo、DoctorID、PatientID、Reason、Timestamp）写入 Fabric 账本。
        4. **患者与监管权责分离**：
        * 患者不承担专业医疗合规的判定，仅对事实做知情确认（点击【确认无异议】或【提出异议】）。
        * 监管人员是系统内**唯一的事件合规审判者**（管理员无权干预医疗合规事件）。
      
      
        5. **监管审查三级状态与分级惩戒（杜绝系统自动永久封号）**：
        * **一级：正常（已确认）**：监管人员核实临床原因合理，事件标记为正常，更新状态为 `CLOSED_APPROVED`，事件归档。
        * **二级：存在疑问（待调查）**：理由不充分、访问数据范围异常的，监管员将事件置为 `UNDER_INVESTIGATION`，要求医生补充诊断报告佐证。
        * **三级：确认违规（分级限制）**：监管人员确认属于假冒抢救或非法刺探，由系统或管理员联动执行阶梯式限制：
        * **NORMAL（正常）**：常规账号状态，可正常使用全部功能。
        * **RESTRICTED（限制访问）**：禁止其跨机构调阅病历及使用紧急访问功能，仅保留本院系统基本操作。
        * **DISABLED（禁用账号）**：账号彻底无法登录系统。

        ### 3.3 基于规则的动态风险评分引擎 (RiskEngine)
      
        系统坚持采用**固定规则加权评分机制**，不引入任何复杂的机器学习算法，确保计算过程透明、可解释、易答辩。
      
        #### 3.3.1 规则加权计算公式
      
        $$R_{\text{total}} = \min\left(100, \sum_{k=1}^{m} w_k \cdot \text{Score}_k\right)$$
      
        #### 3.3.2 固定风险规则表
      
        | 风险维度     | 规则编号 | 判定条件                                                     | 贡献风险分值 |
        | ------------ | -------- | ------------------------------------------------------------ | ------------ |
        | **访问时段** | RULE-T1  | 非工作时间访问（18:00 - 次日 08:00）                         | +20 分       |
        | **机构跨度** | RULE-D1  | 跨医疗机构访问（调阅其他医院病历）                           | +15 分       |
        | **访问频次** | RULE-F1  | 短时间内频繁访问（Redis 5分钟窗口内对同一患者访问 $>3$ 次）  | +25 分       |
        | **批量抓取** | RULE-F2  | 一次访问多个患者（Redis 10分钟窗口内调阅不同患者数 $\ge 5$ 人） | +20 分       |
        | **授权状态** | RULE-A1  | 患者未在线授权（常规跨院访问发起时）                         | +30 分       |
        | **访问类型** | RULE-E1  | 触发紧急访问机制（Break-Glass 申请）                         | +40 分       |
      
        #### 3.3.3 风险区间与处置策略
      
        ```text
          0 分                               30 分                              60 分                      100 分
          ┌───────────────────────────────────┬──────────────────────────────────┬────────────────────────────┐
          │          低风险 (0 - 29 分)        │        中风险 (30 - 59 分)       │      高风险 (60 分以上)     │
          └───────────────────────────────────┴──────────────────────────────────┴────────────────────────────┘
                           │                                   │                               │
                           ▼                                   ▼                               ▼
                    [系统自动允许]                      [需患者在线确认]                  [系统直接拦截阻断]
                (常规审计日志记录)                  (推送确认或走 Break-Glass)        (记录高危日志并触发报警)
        
        ```
      
        * **低风险（0 — 29 分）**：系统自动允许访问（ALLOWED），记录日常审计日志。
      
      
        * **中风险（30 — 59 分）**：挂起请求（PENDING_CONFIRM），要求患者在线授权确认；如遇危急救治则提示转入 Break-Glass 流程。
      
      
        * **高风险（60 分及以上）**：系统直接拒绝访问（REJECTED），记录高危审计日志并向监管端告警。

        ### 3.4 AI Agent 智能辅助查询架构
      
        AI Agent 仅定位为系统**业务查询辅助工具**，其核心原则是“AI 仅做语义解析与调度，业务逻辑与鉴权严格由 Go 后端收口”。
      
        ```text
                            用户在前端聊天框输入自然语言
                   (例如: "查询患者张三最近的胸部CT检验报告")
                                   │
                                   ▼
                     ┌───────────────────────────┐
                     │   Python FastAPI AI Agent │
                     │   1. 语义解析与槽位抽取   │
                     │   2. 匹配对应业务 Tool    │
                     └─────────────┬─────────────┘
                                   │ HTTP 请求 (请求头携带当前用户 JWT Bearer Token)
                                   ▼
                     ┌───────────────────────────┐
                     │        Go 后端网关        │
                     │   1. 解析 JWT 验证用户身份│
                     │   2. 统一权限服务鉴权过滤 │
                     └─────────────┬─────────────┘
                                   │
                     ┌─────────────┴─────────────┐
                     ▼                           ▼
              [鉴权通过: 返回 JSON 数据]     [鉴权失败: 返回 403 Forbidden]
                     │                           │
                     └─────────────┬─────────────┘
                                   ▼
                     ┌───────────────────────────┐
                     │   Python FastAPI AI Agent │
                     │   将数据整合为自然语言输出│
                     └───────────────────────────┘
        
        ```
      
        * **支持的业务查询场景**：
      
      
        * **医生角色**：“查询张三最近的检查记录”、“调阅张三历史用药单”。
      
      
        * **患者角色**：“我现在授权了哪些医生？”、“最近谁调阅了我的病历？”。
      
      
        * **监管角色**：“今天有哪些高风险访问事件？”、“查看最近待审核的紧急访问”。
      
        
      
      
        * **受限工具集定义（严格白名单）**：
      
      
        * `tool_query_medical_records(patient_name, data_type)`
      
        * `tool_query_authorizations(patient_id)`
      
        * `tool_query_audit_logs(risk_level, limit)`
      
        * `tool_verify_integrity(record_no)`
      
        
      
        * **AI 行为禁区（红线原则）**：
      
      
        * 严禁自动修改或删除医疗数据、严禁代患者自动授权或撤销授权；
      
      
        * 严禁自动裁决医生紧急访问是否违规、严禁自动执行封号惩戒；
      
      
        * 严禁直接通过网络或驱动操作 Fabric 智能合约与底层 MySQL/IPFS。

        ## 5. 区块链智能合约 (Chaincode) 接口规范
      
        链码基于 Go 语言开发，部署于通道 `medicalchannel`，只负责存证摘要与关键流转记录，不承担复杂的加密运算或数据存储：
      
        ```go
        package chaincode
        
        // MedicalAsset 医疗存证资产
        type MedicalAsset struct {
            RecordID   string `json:"record_id"`   // 病历编号
            PatientID  string `json:"patient_id"`  // 患者编号
            CID        string `json:"cid"`         // IPFS 密文寻址哈希
            FileHash   string `json:"file_hash"`   // 明文 SHA-256 摘要
            HospitalID string `json:"hospital_id"` // 开具医院代码
            CreatorID  string `json:"creator_id"`  // 签署医生代码
            CreateTime string `json:"create_time"` // 存证时间戳
        }
        
        // EmergencyAccessRecord 紧急访问上链存证凭据
        type EmergencyAccessRecord struct {
            EventNo    string `json:"event_no"`    // 紧急事件编号
        ```

        ### 6.2 统一权限评估与紧急访问逻辑 (`service/access_engine.go`)
      
        ```go
        package service
        
        import (
            "errors"
            "time"
        )
        
        type AccessEngine struct {
            // 依赖注入各持久化 Repository 与 RiskEngine
        }
        
        type AccessDecision struct {
            Allowed     bool   `json:"allowed"`
            IsEmergency bool   `json:"is_emergency"`
            Decision    string `json:"decision"` // ALLOWED, NEED_BREAK_GLASS, PENDING_CONFIRM, REJECTED
            Reason      string `json:"reason"`
        }
        
        // EvaluateAccess 执行统一的权限与紧急访问评估
        func (e *AccessEngine) EvaluateAccess(doctorID, patientID, recordID uint64, isEmergency bool) (*AccessDecision, error) {
            // 1. 基础身份前置安全核验 (ABAC 医生端属性)
            doctor, err := e.getDoctorProfile(doctorID)
            if err != nil || doctor.Role != "doctor" {
                return &AccessDecision{Allowed: false, Decision: "REJECTED", Reason: "非合法医生身份"}, nil
            }
            if doctor.Status == "DISABLED" {
                return &AccessDecision{Allowed: false, Decision: "REJECTED", Reason: "医生账号已被禁用，禁止访问"}, nil
            }
            if doctor.Status == "RESTRICTED" && isEmergency {
                return &AccessDecision{Allowed: false, Decision: "REJECTED", Reason: "该医生账号已被监管限制跨机构紧急访问权限"}, nil
            }
        
            // 2. 检查患者显式授权 (常规访问)
            hasConsent := e.checkValidAuthorization(patientID, doctorID, doctor.HospitalID, recordID)
            if hasConsent {
                // 计算动态风险评分
                riskScore := e.calculateRiskScore(doctor, recordID, isEmergency)
                if riskScore < 30 {
                    return &AccessDecision{Allowed: true, Decision: "ALLOWED", Reason: "常规授权有效，低风险放行"}, nil
                } else if riskScore < 60 {
                    return &AccessDecision{Allowed: false, Decision: "PENDING_CONFIRM", Reason: "中风险操作，等待患者在线确认"}, nil
                } else {
                    return &AccessDecision{Allowed: false, Decision: "REJECTED", Reason: "高风险操作，系统安全拦截"}, nil
                }
            }
        
            // 3. 无有效授权场景处理
            if !isEmergency {
                return &AccessDecision{Allowed: false, Decision: "NEED_BREAK_GLASS", Reason: "未取得患者授权，危急场景可申请紧急访问"}, nil
            }
        
            // 4. 紧急访问 (Break-Glass) 申请放行
            return &AccessDecision{
                Allowed:     true,
                IsEmergency: true,
                Decision:    "BREAK_GLASS_ALLOWED",
                Reason:      "紧急抢救申请已核准放行，生成待审核事件单并全量存证",
            }, nil
        }
        
        ```

        ## 10. 最终系统规划评价与答辩问答自洽准备
      
        ### 10.1 系统设计优点自查
      
        * **论文主题明确、边界严密**：紧扣“区块链可信共享 + 动态访问控制 + AI Agent 辅助”，完全符合本科毕业设计工作量与深度要求。
      
      
        * **存储与区块链分工合理**：采用“链下 IPFS 存密文 + 链上 Fabric 存摘要”，既保障了大文件吞吐效率，又解决了隐私防篡改难题。
      
      
        * **安全架构高度统一**：设立单一安全网关收口权限校验，消除了各模块重复鉴权与业务耦合。
      
      
        * **紧急访问具有真实场景价值**：设计严密的 Break-Glass 机制与监管闭环，既解决了急诊抢救无法在线授权的现实难题，又避免了权限滥用。
        * **AI Agent 定位正确且受控**：纯作为查询代理运行，绝不越权直连数据库，安全机制无漏洞。
      
        
      
        ### 10.2 答辩核心质询自洽标准回答
      
        * **问题一：老师提问：“如果患者处于昏迷或突发危重急救，无法在线完成授权，你的系统怎么处理？会不会因为权限太死而耽误抢救？”**
        > **回答**：系统设计了**紧急访问（Break-Glass）机制**。在遇到患者昏迷等突发危急场景时，医生可以在完成基础身份核验并签署临床责任声明后临时调阅患者关键病历。同时，系统会自动生成不可篡改的紧急访问事件单并写入 Fabric 联盟链，向患者和监管人员发送双向通知。救治完成后由监管人员对事件进行独立审核，如果确认属于虚假抢救，系统将根据情节轻重对医生账号进行限制访问或停用惩戒，实现救急与安全的平衡。
      
      
        * **问题二：老师提问：“你的动态访问控制和风险评分是怎么实现的？用了什么 AI 模型？数据集怎么训练的？”**
        > **回答**：本系统在风险评分上**没有采用黑盒的机器学习或深度学习模型**，而是基于医疗数据流转的真实特征，设计了**基于固定规则的动态加权评分引擎**。系统从“访问时段（是否非工作时间）”、“机构跨度（是否跨院）”、“访问频次（是否短时间高频调阅）”、“访问范围（是否单次批量调阅多名患者）”等维度量化计算综合风险分，并根据阈值划分低、中、高三个风险等级执行放行、确认或拦截策略。这种设计可解释性强、计算开销小，适合工程落地与答辩展示。
      
      
        * **问题三：老师提问：“你的系统引入了 AI Agent，如果黑客通过自然语言提示词让 AI 帮他调阅全院病历，会不会绕过你的区块链和访问控制系统？”**
        > **回答**：绝对不会。本系统中的 **AI Agent 严禁直接连接 MySQL 数据库或区块链节点**，它仅充当自然语言语义解析器。AI 提取意图后，必须通过受控的 Tool Calling 携带当前登录用户的 JWT Bearer Token 请求 Go 后端的标准 API 接口。Go 后端的统一安全网关会严格执行 RBAC 角色、ABAC 属性、患者授权以及风险评分的多重过滤。如果调用者自身没有该患者的授权，AI 调用后端接口同样会收到 HTTP 403 拒绝响应，AI 随后会如实向用户反馈无权访问，因此全流程严格受控于系统的安全防线之内。
        >
        >
